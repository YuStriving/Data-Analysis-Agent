# 详细设计：方案为什么这样做

这里记录具体技术方案。它帮助开发者理解：方案怎样满足已经确认的需求，以及为什么选择这种做法。第一次阅读时，先看本页，再到[设计索引](index.md)找相关方案。

## 本目录里的内容

| 文件或文件夹 | 用途 |
| --- | --- |
| `README.md` | 本页：说明本目录怎么用 |
| `index.md` | 设计目录：列出已有方案和每份方案适用的问题 |
| `template.md` | 新建设计说明时可复制的模板；不适用的章节可以删掉 |
| `core-beliefs.md` | 解释项目长期采用的设计原则和原因；它不是功能清单 |
| `cross-module/` | 放需要多个模块配合的方案；目前其中有工具执行与授权设计 |
| `cross-module/tool-execution-authorization.md` | 说明 Java、Python 和工具执行各自负责哪些授权检查 |

这里只列当前存在的文件和文件夹。还没有实际设计内容的主题，不先创建空目录或占位文档。

## 遇到不同问题该看什么

| 问题 | 去哪里找 |
| --- | --- |
| 系统有哪些模块，模块现在怎样连接 | [架构地图](../architecture/README.md) |
| 某个模块必须遵守哪些项目规则 | [总体设计约束](../DESIGN.md) |
| 用户要求系统表现成什么样 | [需求说明（Spec）](../spec/README.md) 和对应需求文件 |
| 为什么采用某种技术方案 | 本目录中的正文，从 [index.md](index.md) 查找 |
| 这一次怎样实施、实际验证了什么 | [实施计划（Plan）](../exec-plans/README.md) 和对应计划 |

简单说，需求说明讲“要做什么”，详细设计讲“方案怎么满足需求”，计划讲“这次怎么实施”。设计中的预期结果不是已经实现或通过验证的证明。

## 阅读或新增方案

阅读时，先看索引找到对应正文，再确认正文开头的状态：`proposed` 是讨论中的方案，`accepted` 是已经确认的方案，`deprecated` 表示不再推荐，`superseded` 表示已有新方案替代。状态说明方案是否确认，不说明代码是否完成。

新增时，先确认需求和当前实现，再从[模板](template.md)开始；只在有多份相关正文需要分组时新建子目录。完成正文后，把链接、负责范围和适用说明登记到 [index.md](index.md)。如果方案会改变已确认的用户行为或接口，先更新并确认对应需求说明。
