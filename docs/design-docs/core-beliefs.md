# 核心设计信念

本文件解释长期工程原则、理由及使用方式。总体约束与导航见 [DESIGN](../DESIGN.md)，
具体机制见 [详细设计索引](index.md)；硬性边界由唯一的 [根规范](../../AGENTS.md) 与已确认 Spec 决定，模块入口见相应 README。
原则用于评估方案，不代表对应能力已经实现或验证，也不能作为放宽现有安全边界的理由。

## 1. 每种知识有唯一的权威来源

**原则：**架构地图描述组成与职责，DESIGN 规定总体约束，详细设计解释方案与取舍，
Spec 定义行为与验收要求，Plan 或交付说明记录单次验证结果，可执行测试与代码同放模块；Agent 需要重复执行的验证流程写入适用的 quality Skill。索引链接正文，不复制正文。

**理由：**同一事实维护在多个地方容易出现版本冲突，人和 AI 会据不同入口执行不同要求。
明确唯一来源能让修改、审查与恢复任务有稳定依据。

**项目实例：**工具的授权返回约定以 [工具 Spec](../spec/tool-calling/spec.md) 为准，
[设计正文](cross-module/tool-execution-authorization.md) 解释为何采用同步 None/异常；索引不再复制接口定义。

**审查问题：**这条行为或约束应在哪里维护？其他入口能否只链接它？当前读取的是草稿、历史记录还是现行契约？

**边界：**不同文档可提供摘要与导航，但不能成为另一个独立规范；文档与代码冲突时先核实，不能自动以更新日期覆盖已确认契约。

## 2. 状态有明确所有者，派生视图不变成第二份事实

**原则：**每个授权、任务状态、版本或持久化事实有明确提供者。缓存、界面状态与派生字段允许存在，
但须说明来源、同步或失效条件，以及来源不一致时如何处理。

**理由：**禁止一切重复表示会妨碍缓存和展示；真正需要避免的是多个地方各自决定同一事实，且没有一致性关系。

**项目实例：**工具请求从 context 读取 tool_version，执行配置检查同一版本；Java 是最终权限来源。
memory 的热上下文提供复用视图，不代替授权，也不等同于 checkpoint 的恢复状态。

**审查问题：**谁可以修改这个事实？缓存失效或不同步时使用什么来源？重复字段是兼容投影还是另一套独立状态？

**边界：**缓存和默认值不得扩大授权范围；界面权限提示不能授权，旧记忆也不能恢复已经撤销的数据访问权。

## 3. 优先组合与显式注入，减少复制流程

**原则：**复用稳定的执行契约，通过入口、工厂或图构建处注入具体工具、资源与策略。
需要差异时先判断是否能组合已有能力，而不是复制整条执行链。

**理由：**授权、错误处理、超时和验证复制多份后容易只修好其中一条；显式组合能看到依赖来源，也便于替换测试依赖。

**项目实例：**ToolExecutor 注入 authorize 和固定配置，ToolAuthorizationGate 注入策略查询与业务检查，
而不是在执行器里按业务名称构造数据分析依赖。

**审查问题：**新增业务是否可以只提供适配和策略？依赖在哪里装配？复制出去的流程会不会遗漏拒绝检查？

**边界：**不为表面相似强行抽象；复用安全检查前先确认等效拒绝路径，不通过允许所有请求的假策略绕过原检查。

## 4. 职责围绕稳定契约分离

**原则：**通用层处理稳定契约与执行，业务层处理规则和资源适配；不同所有权或变化原因的模块保持明确分工。

**理由：**职责混合会让一个节点改动牵动存储、提示词、权限和展示，增加定位与回归成本。

**项目实例：**ContextBuilder 产生节点资料视图，Prompt/Node Skill 负责文本职责，tool_calling 执行工具，
memory 保存可复用事实，checkpoint 负责恢复位置；Java/Python/前端的最终责任遵循根规范。

**审查问题：**这段逻辑的输入输出是什么？谁负责业务拒绝？为什么放在这个模块，而不是它的调用方或资源适配器？

**边界：**共享契约或存储适配器可以复用，业务策略和状态所有权不因此合并。具体要求见
[总体架构不变量](../DESIGN.md#2-architectural-invariants)及[Python Agent README](../../backend-agent/README.md)。

## 5. 复杂度由当前问题支撑

**原则：**优先现有模块、清晰数据类型和最小变化点；新增抽象、协议、目录或子计划必须对应真实问题和可验证收益。

**理由：**过早引入动态框架或多层分类会增加维护与 AI 理解成本，掩盖尚未完成的关键路径。

**项目实例：**计划先分 governance、features、maintenance 三类；需要新类型时再扩展。
上下文当前字符裁剪不自动升级为 embedding 召回或智能 token 压缩；新增这些能力需独立设计与评估。

**审查问题：**当前哪项需求需要这一层？更直接的方案能否满足？它是否有独立完成判据和维护者？

**边界：**简单不能牺牲授权、隔离、错误信息或必要验证。小事项的 Spec 适用条件见
[Spec 协作约定](../spec/README.md#spec-适用条件)；任务分类及是否需要 Plan 按
[协作执行规范](../WORKFLOW.md) 与 [Plan 工作流](../exec-plans/README.md) 执行。

## 6. 正确性由可复核证据确认

**原则：**分别记录设计目标、当前实现和实际验证。保留拒绝原因、失败信息与未验证项，满足必要证据后才标记完成。

**理由：**文件存在、代码可读或计划已勾选都不能证明真实行为；混淆预期与结果会误导下一位执行者。

**项目实例：**文档检查证明入口与链接可达；工具拒绝需相应用例；Memory Fake Store 用例不能证明真实 Redis/Mongo 部署可靠性。
本次设计补充只核对源码与测试定义，不把历史测试数字当作新结果。

**审查问题：**这个结论由源码、测试还是部署证据支持？实际执行了什么？失败与未执行项在哪里记录？

**边界：**验证优先关键路径，不机械要求全量测试。安全变化包含拒绝场景，未通过或缺关键证据的计划保持未完成。
单次验证结果记录在对应 Plan；Agent 需要重复执行的验证流程写入适用的 quality Skill。
