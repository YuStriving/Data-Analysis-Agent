# MVP 阶段按风险开展 Agent 协作

项目处于 MVP 开发阶段，原协作规则要求维护 Spec、落库 Plan 并经过多轮确认，用户已删除相关流程文档，希望减少开发负担和提前设计。本次讨论确认：取消强制 Spec/Plan 与重复审批，按任务风险决定确认时机，同时保留现有职责边界、安全底线和关键功能验证。

## 已确认的决策

- 局部、低风险且需求清楚的任务，Agent 检查现状并说明简要方案后直接实施；多步骤任务拆成可验证的小步，不强制创建 Spec、Plan 或 ADR。
- 重要接口、数据模型、跨模块职责或安全边界变化，以及核心框架替换、破坏性操作，先说明影响与方案并取得确认；已有明确确认不重复审批，范围实质扩大时重新确认。
- 优先完成本次确认的最小可运行业务闭环。新增抽象和依赖必须解决当前问题，不为假设中的未来需求提前增加架构层次。
- Java 保持认证、授权和数据范围控制的最终责任；Python 在授权上下文内编排执行，前端负责交互展示。保留只读 SQL、最小权限、密钥保护和安全失败处理要求。
- 验证与改动风险匹配，优先关键路径；权限和数据访问控制变更必须验证拒绝场景。交付记录实际检查结果、未验证项和阻塞，明确区分已实现、模拟与规划能力。

## 采用这一方案的原因与取舍

原流程提供独立的需求与计划记录，但要求每项适用任务维护多份文件并等待分阶段确认。当前阶段选择在对话中明确目标、范围与验收，将实施质量落实到代码和验证证据，降低流程维护成本。

这一选择减少了独立文档的追溯信息，因此重要取舍、范围变化和实际验证结果仍需在交付说明中写清。需要更强的需求追溯时，再根据具体问题与用户讨论文档形式，不自动恢复整套旧流程。

本记录只涉及协作方式；具体 MVP 功能范围仍以用户确认的任务为准，不从现存模块规划中推导额外交付要求，也不表示任务执行、SSE 或审计等能力均已实现。
