# 实施计划：记录这次改动

Plan（实施计划）像一份任务清单和进度记录：它写明这次准备改什么、按什么顺序做、怎样检查，以及最后实际发生了什么。“验收”就是按需求中的条件确认改动是否做好。Plan 不代替[需求说明（Spec）](../spec/README.md)，也不重复详细技术方案。

## 什么时候需要计划

需要分步骤完成的任务称为 Normal；跨模块或范围、风险较大的任务称为 Complex，这两类需要 Plan。局部、低风险的小改动称为 Micro，通常可以不建计划。具体判断方法见[协作执行规范](../WORKFLOW.md#协作状态机)。

Spec 回答“系统应该怎样表现”，Plan 回答“这次准备怎样改”。是否需要 Spec 和是否需要 Plan 是两件事，按各自的规则判断。

## 计划放在哪里

| 文件夹或文件 | 用途 |
| --- | --- |
| `README.md` | 本页：说明计划如何创建、更新和归档 |
| `template.md` | 新建简版计划时复制的模板 |
| `active/` | 正在准备、实施或验收的计划 |
| `completed/` | 必要验收通过后归档的计划 |
| `governance/` | 修改规则、文档和协作方式的计划 |
| `features/` | 增加产品能力的计划 |
| `maintenance/` | 修复或维护已有功能、文档和基础设施的计划 |

三个类别分别在 `active/` 和 `completed/` 下使用。按计划的主要目的选一个类别，不要复制同一计划到多个地方。

## 计划状态和怎么开始

| 状态 | 简单含义 | 下一步 |
| --- | --- | --- |
| `draft` | 草稿，等用户审阅 | 按意见修改；此时不开始计划内的实现 |
| `ready` | 用户已确认，可以开工 | 记录确认日期和批准范围，然后开始 |
| `in_progress` | 正在实施 | 随进度更新步骤和范围 |
| `verify` | 实施完成，正在检查 | 通过后完成；失败时修复并重新检查 |
| `done` | 验收通过、记录完整 | 移到对应的 `completed/` 文件夹 |

使用计划模式讨论任务时，只先给出方案。进入实施阶段后，先把最终计划保存为 `draft` 并请用户审阅；只有用户确认落盘版本后，才能记为 `ready` 并开始实现。用户要求修改时，更新草稿并再次等待确认。

如果计划因问题或检查失败留在 `active/`，之后继续修复时要接着更新原计划。修复后必要检查通过，就在同一轮补齐结果和证据、设为 `done`、移入 `completed/` 并修正相关链接，不用等用户再提醒。若仍有失败或关键事项未检查，继续留在 `active/verify` 并写明原因。

工作区问题、用户暂停或关键场景尚未验证时，不能标为 `done`。范围或已确认的行为改变时，先更新并确认相关 Spec；不能只改 Plan 来改变需求。

## 简版计划和复杂计划

一般任务复制[简版 Plan 模板](template.md)。复杂任务在简版基础上补充：当前问题的依据、最小目标和不做的内容、受影响模块与接口、风险和依赖、每一步的完成标准，以及实际验证和剩余事项。不要把完整 Spec 或全部测试用例复制进 Plan。

计划中的每一步应能检查是否完成。计划状态必须和所在目录一致：`active/` 里不能是 `done`，`completed/` 里的状态必须是 `done`。

## 完成时记录什么

在计划中记录实际修改、运行过的命令、结果、证据位置和没有执行的检查及原因。没有可复用经验时，写明“无可复用结论”；有经验可供其他任务复用时，更新对应的权威文档并链接到它。不要为了归档另建一次性报告。

归档时使用原文件名，确认目标位置没有同名文件，并更新所有指向旧位置的链接。从仓库根目录运行 `python scripts/ci/check-docs.py` 检查文档链接。
