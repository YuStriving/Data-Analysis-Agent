# 需求说明：先说清楚系统应该怎样表现

Spec（需求说明）写明用户能看到什么结果、接口怎样回应、出错时应该怎样处理。它让开发者、测试人员和产品人员对“做对了是什么样”有共同理解；它不负责安排本次改动的实施步骤。

## 本目录里的文件和文件夹

| 文件或文件夹 | 用途 |
| --- | --- |
| `README.md` | 本页：说明什么时候需要需求说明，以及如何维护它 |
| `template.md` | 新建事项需求说明时复制的模板 |
| `tool-calling/` | 工具调用功能的专属需求和历史实施记录 |
| `tool-calling/spec.md` | 当前工具调用行为与接口要求的主要依据 |
| `tool-calling/tasks.md` | 过去的实施记录；新任务使用 `docs/exec-plans/` 中的 Plan |

## Spec 适用条件

先找找是否已有相关的需求说明。下列情况通常需要新建或更新 Spec：

- 增加或改变用户能看到的功能、多个模块之间的行为或公开接口。
- 改变数据保存方式、权限、安全、隐私、审计或租户隔离规则。
- 改变架构边界，或还存在必须先由用户决定的问题。

局部文案调整或单页面的小修改，若不影响接口、数据、权限、安全和已确认要求，且目标与检查方法都清楚，通常可以直接实施，不用新建 Spec。拿不准时，先检查现有 Spec 并确认是否需要更新。

## 确认后怎样修改

已确认的 Spec 就是当前行为约定。实施中发现需求有变化时，先更新相应内容并取得确认，再继续实现。不能只改计划或设计文档来悄悄改变已确认的要求。

设计说明解释技术方案；Plan 记录本次要做的步骤、进度和实际验证结果。简单说，Spec 说明“应该怎样”，设计说明“为什么采用这个方案”，Plan 说明“这次怎样完成”。

## 验收与测试记录

每项需求都应有能判断是否完成的验收条件。真正运行过的测试和检查结果记入本次 Plan 或交付说明；可执行测试代码和测试用例留在对应模块。Agent 需要跨任务重复执行的验证流程归入适用的 quality Skill，不在 Spec 里另建一次性测试报告。

## 创建 Spec 与使用模板

新事项需求说明放在 `docs/spec/<事项名>/spec.md`。先检查是否有可复用的 Spec，再复制[模板](template.md)，替换示例内容并按需裁剪。只链接已经存在的文档。
