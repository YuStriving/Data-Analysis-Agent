# Normal/Complex 任务保存计划

适用于本仓库需要 Plan 的协作任务。先定位仓库根目录，遵守唯一的根目录
`AGENTS.md`；模块入口与局部实现说明见对应 README。读取[协作执行规范](../../../docs/WORKFLOW.md)、
[计划工作流](../../../docs/exec-plans/README.md) 与[Spec 协作约定](../../../docs/spec/README.md)。
分类、Plan 状态与模板以工作流文档为准；本 Skill 不替代 Spec 或实施授权。

## 工作步骤

1. 检查用户目标、授权范围、工作区已有改动和适用规范；先调查当前实现及现有 Spec/Plan。
2. 按协作执行规范的影响、风险和不确定性分类。Micro 免 Plan；是否需要 Spec
   另按 Spec 协作约定判断。若范围、风险或已确认行为/契约发生变化，升级分类并回到相应 Gate。
3. Normal 准备简版 Plan 内容；Complex 准备完整 Plan 内容。两类任务的 Spec 适用性均按 Spec 协作约定独立判断；适用 Spec 需要确认时，先讨论并确认，再定稿 Plan 内容。
   已确认行为或契约需要变化时，先更新并确认 Spec，再更新 Plan；不得仅改 Plan 改变要求。
4. Codex 原生 Plan 模式只输出方案，不写文件。用户同意提案并切换到实施模式后，先保存最终 Normal/Complex Plan 为 `draft`，说明文件路径和范围，然后暂停；提案确认只授权保存 Plan，不授权开始实现。
5. 只有用户明确审阅确认落库 Plan 后，才在 Plan 记录确认日期与批准范围、将状态改为 `ready` 并实施。用户要求修改时，更新 Plan、保持 `draft` 并再次暂停；沉默或含糊答复不算批准。实质改变已批准范围、契约或验收时，更新 Plan 并重新审阅；不得超出确认范围实施。
6. Micro 不创建 Plan，也不经过 Plan 审阅 Gate。关键需求或 Spec 未决时先解决，不把假设写成已确认要求；需要改变已确认行为/契约时先过 Spec Change Gate。
7. 持续更新所需 Plan 的状态与进展；本次命令、结果和未验证项记入 Plan。需要 Agent 重复执行的验证流程归入适用的 quality Skill。
8. 结束时做轻量知识分流：无可复用结论时在 Plan 中注明；有结论时更新权威文档并链接，不复制一次性验证结果。
9. 只有必要验证通过、证据齐全且 Plan 状态为 `done` 后，才归档到同类别 `completed/`；未完成或受阻计划留在 `active/` 并记录原因。
   若此前因问题或验证失败留在 active，后续继续修复时更新原 Plan；修复后必要验收一旦通过，
   同一轮主动补齐结果与证据、将状态改为 `done`、移入 `completed/` 并修正引用，不等待用户再次提醒。
   若问题已修复但验收仍失败或关键项未验证，记录结果并保留在 `active/verify`。

## 触发边界

- Micro：局部、低风险、目标与验收明确，且不改变已确认行为/契约或安全边界；免 Plan，Spec 是否必需按 Spec 协作约定判断。
- Normal：范围明确但需要分步实施；保存简版 Plan，是否需要 Spec 按 Spec 协作约定判断。
- Complex：跨模块、新契约或数据模型、架构/安全边界变化，或关键需求未决；保存完整 Plan，Spec 是否必需按 Spec 协作约定判断，需要时先确认再保存 Plan。
- 纯咨询、翻译、只读审查和检查不创建实施 Plan；开始修复时重新分类。
- 计划模式只输出方案和预定路径，不写文件；进入实施模式后，先保存所需的 Spec/Plan，Plan 保存后须等待用户审阅确认。
- 不因调用本 Skill 获得提交、推送、发布或放宽安全边界的授权。
